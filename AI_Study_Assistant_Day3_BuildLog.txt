Day 3 Build Log: Text Extraction
What was built, why it was built, how it works, what problems came up, and how we fixed them

Day 3 Overview
Day 3 goal was to take uploaded study files and extract their raw text automatically. This meant the app had to process both PDFs and images after upload, save the extracted text into MongoDB, and mark each document as processed. By the end of Day 3, the app could upload a file, fetch it back from Cloudinary, extract text from it, store that text in the database, and show a preview on the dashboard.

What Was Built
	- app/api/process/[id]/route.ts: Backend API route that processes one uploaded document, extracts text, and updates MongoDB.
	- components/FileUpload.tsx: Updated so the upload flow now calls the processing route after upload succeeds.
	- app/dashboard/page.tsx: Updated to show an extracted text preview on the dashboard.
	- next.config.ts: Updated to treat unpdf and tesseract.js as server-side external packages.
	- package.json: Includes the libraries needed for PDF extraction and OCR.

Why Text Extraction Was Needed
File upload by itself is not enough for an AI study assistant. The AI cannot generate summaries, flashcards, or quizzes directly from a PDF file or image file. It first needs plain text. That is why Day 3 matters so much: it creates the bridge between file storage and AI features. Once a document's text is stored in MongoDB, Days 4 and 5 can use that text for summaries, flashcards, and quizzes.

Key Libraries Used
What is unpdf? unpdf is a PDF text extraction library. We used it to read the binary data of an uploaded PDF and turn it into a plain text string.

What is tesseract.js? tesseract.js is an OCR library. OCR means Optical Character Recognition. It looks at an image and detects letters and words from that image, then returns them as text.

Why both were needed
	- PDF files need a PDF parser because their text is stored in document structure.
	- Image files need OCR because images do not contain raw text data.
	- Using both lets the app support typed notes and photographed or scanned notes.

How the Day 3 Flow Works
1. User uploads a PDF or image from the dashboard.
2. /api/upload saves the file to Cloudinary.
3. MongoDB stores the document metadata like file name, file URL, and file type.
4. The frontend then calls /api/process/:id.
5. The processing route finds the document in MongoDB using the document ID.
6. The route fetches the uploaded file back from Cloudinary using fileUrl.
7. If the file is a PDF, unpdf extracts the text.
8. If the file is an image, tesseract.js runs OCR and extracts the text.
9. The route saves the extracted text into extractedText.
10. The route updates the document status from uploaded to processed.
11. The dashboard refreshes and shows the processed file with a text preview.

Main File: app/api/process/[id]/route.ts
What this file does This route is the engine of Day 3. It receives a document ID, loads that document from MongoDB, downloads the real file from Cloudinary, extracts its text, and writes the result back into the document record.

How PDF extraction works When the document's fileType is application/pdf, the route sends the file buffer into unpdf. The result is merged into one final text string.

How image OCR works When the document's fileType starts with image/, the route sends the file buffer into Tesseract.recognize(...). Tesseract reads the image and returns the detected text.

Why we set runtime = "nodejs" PDF parsing and OCR libraries work better in the Node.js runtime than in the Edge runtime. Forcing Node.js makes the route more stable.

Frontend Change: components/FileUpload.tsx
Day 2 only uploaded files. Day 3 extended that flow by making the frontend call the processing API right after upload succeeds. That means the user still uploads only once, but behind the scenes the app does two things: upload the file and process the file for text extraction. We also improved the error message so the frontend can show the real backend problem if processing fails.

Dashboard Change: app/dashboard/page.tsx
The dashboard originally showed only file name, type, and status. For Day 3, that was not enough because we needed visible proof that extraction actually worked. So we added an Extracted Text section to each document card. This shows a preview of the saved text directly from MongoDB.

Problems We Hit and How We Fixed Them
1. Wrong MongoDB access style
The first version of the processing route used native MongoDB client logic, but the project was already built with Mongoose. We fixed it by using connectDB(), Document.findById(...), and Document.findByIdAndUpdate(...).

2. Cloudinary fetch failed
The upload worked, but text extraction failed because the backend could not fetch the PDF back from the saved Cloudinary URL. The real issue was that Cloudinary PDF delivery was restricted. We fixed it by enabling PDF and ZIP delivery in Cloudinary settings.

3. Backend errors were hidden
At first, the frontend only showed a generic failure message. We updated the process route to return the real error message and updated the frontend to display it.

Environment and Package Notes
No brand-new secret keys were needed specifically for Day 3, but the processing system depends on Cloudinary environment variables, the MongoDB connection string, and installed npm packages like unpdf and tesseract.js.

Day 3 Complete
User can log in -> upload a PDF or image -> file saves to Cloudinary -> processing route fetches the file -> text is extracted -> text is saved to MongoDB -> document status becomes processed -> extracted text preview appears on the dashboard.

What Comes Next
Day 4 can now use extractedText as input for AI-generated summaries. Since Day 3 built the text foundation, the next step is to send that saved text into Gemini and store the generated summary back in MongoDB.
